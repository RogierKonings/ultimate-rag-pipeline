# Epic 8.5: Rust Testing, Migration, and Deployment

> **Priority:** High
> **Estimated Effort:** 6-8 weeks
> **Dependencies:** Epics 8.1-8.4
> **Parent Epic:** [08-rust-rewrite-overview.md](08-rust-rewrite-overview.md)

## Overview

This epic covers the testing strategy, migration plan, and deployment configuration for the Rust rewrite. It ensures feature parity, provides migration tooling, and establishes CI/CD pipelines for Rust services.

## Goals

- Establish comprehensive testing strategy
- Create parallel running capability (Python + Rust)
- Build migration tooling and data validation
- Set up CI/CD for Rust services
- Create deployment manifests (Docker, Kubernetes)
- Document operational runbooks

## User Stories

### US-8.5.1: Unit Testing Framework
**As a** developer
**I want** comprehensive unit tests
**So that** code correctness is verified

**Acceptance Criteria:**
- [ ] Unit tests for all business logic
- [ ] Mock traits for external dependencies
- [ ] Test coverage measurement
- [ ] Property-based testing for algorithms
- [ ] Snapshot testing for API responses

**Rust Testing Crates:**
- `mockall` - Mocking framework
- `proptest` - Property-based testing
- `insta` - Snapshot testing
- `tokio-test` - Async test utilities

### US-8.5.2: Integration Testing
**As a** developer
**I want** integration tests against real services
**So that** external integrations work correctly

**Acceptance Criteria:**
- [ ] Testcontainers for PostgreSQL, Redis, Qdrant, OpenSearch
- [ ] Test fixtures with sample data
- [ ] API integration tests
- [ ] Database migration tests
- [ ] Cross-service integration tests

**Rust Crates:** `testcontainers`

### US-8.5.3: Behavior Parity Tests
**As a** developer
**I want** tests that verify Rust matches Python behavior
**So that** migration doesn't change functionality

**Acceptance Criteria:**
- [ ] Golden file tests from Python output
- [ ] Chunking output comparison
- [ ] Search result comparison
- [ ] API response comparison
- [ ] Edge case documentation

**Approach:**
1. Generate test cases from Python implementation
2. Save expected outputs as golden files
3. Run same inputs through Rust
4. Compare outputs

### US-8.5.8: CI/CD Pipeline
**As a** developer
**I want** automated CI/CD for Rust
**So that** code is tested and deployed automatically

**Acceptance Criteria:**
- [ ] GitHub Actions workflow for Rust
- [ ] Build matrix (stable, beta, nightly)
- [ ] Clippy linting
- [ ] Rustfmt checking
- [ ] Security audit (cargo-audit)
- [ ] Container image building
- [ ] Automated deployment to staging

**GitHub Actions Workflow:**
```yaml
name: Rust CI

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - uses: Swatinem/rust-cache@v2
      - run: cargo fmt --check
      - run: cargo clippy -- -D warnings
      - run: cargo test
      - run: cargo audit
```

### US-8.5.9: Docker Images
**As an** operator
**I want** optimized Docker images
**So that** containers are small and fast

**Acceptance Criteria:**
- [ ] Multi-stage builds
- [ ] Static linking (musl)
- [ ] Minimal base image (distroless/scratch)
- [ ] Layer caching optimization
- [ ] Image size < 50MB per service
- [ ] Health check endpoints

**Dockerfile Template:**
```dockerfile
FROM rust:1.75-bookworm AS builder
WORKDIR /app
COPY . .
RUN cargo build --release

FROM gcr.io/distroless/cc-debian12
COPY --from=builder /app/target/release/service /
CMD ["/service"]
```

### US-8.5.13: Gradual Migration Plan
**As a** team lead
**I want** a phased migration plan
**So that** risk is minimized

**Migration Phases:**

**Phase 1: Foundation (Weeks 1-12)**
- Rust shared libraries complete
- Unit and integration tests passing
- CI/CD pipeline operational

**Phase 2: Retrieval Service (Weeks 13-20)**
- Rust retrieval in shadow mode
- Performance benchmarks show improvement
- Gradual traffic shift (1% → 10% → 50% → 100%)

**Phase 3: Ingestion Service (Weeks 21-34)**
- Rust ingestion processing new documents
- Parallel processing validation
- Full cutover after validation

**Phase 4: Orchestrator Service (Weeks 35-50)**
- Rust orchestrator in shadow mode
- Extensive behavior comparison
- Gradual traffic shift
- Python deprecation

**Phase 5: Cleanup (Weeks 51-56)**
- Python codebase archived
- Documentation finalized
- Team training complete

## Risk Mitigation

### Testing Coverage Risk
- Aim for >80% code coverage
- Focus on edge cases from Python experience
- Fuzzing for parsing code

### Migration Risk
- Always maintain Python fallback
- Canary deployments
- Feature flags for instant rollback

### Operational Risk
- Train ops team on Rust debugging
- Create comprehensive runbooks
- 24/7 support during migration
