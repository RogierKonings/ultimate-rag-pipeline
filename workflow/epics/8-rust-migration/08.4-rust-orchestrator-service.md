# Epic 8.4: Rust Orchestrator Service

> **Priority:** High
> **Estimated Effort:** 12-16 weeks
> **Dependencies:** Epic 8.1 (Rust Foundation), Epic 8.2 (Rust Retrieval)
> **Parent Epic:** [08-rust-rewrite-overview.md](08-rust-rewrite-overview.md)

## Overview

Rewrite the orchestrator service in Rust. This is the **most challenging** service to port because LangGraph (the Python workflow engine) has no Rust equivalent. The orchestrator must be redesigned using Rust-native state machine patterns while preserving the RAG workflow semantics.

## Goals

- Design and implement Rust state machine for RAG workflows
- Port prompt building with Jinja-like templates
- Implement streaming response support
- Port guardrails (input/output validation)
- Implement conversation memory
- Create LLM gateway client
- Match existing workflow behavior

## Why This Is Hard

### LangGraph Has No Rust Equivalent

LangGraph provides:
- Declarative workflow graphs
- Conditional branching
- State management
- Checkpointing
- Streaming intermediate results

In Rust, we must implement these concepts manually or adapt a generic state machine library.

### Recommended Approach

Use `async-trait` and a custom state machine pattern:

```rust
#[derive(Clone)]
pub struct RAGState {
    pub query: String,
    pub strategy: RoutingStrategy,
    pub context: Vec<RetrievedChunk>,
    pub response: Option<String>,
    pub error: Option<String>,
}

#[async_trait]
pub trait WorkflowNode: Send + Sync {
    async fn execute(&self, state: RAGState) -> Result<RAGState>;
    fn name(&self) -> &'static str;
}

pub struct RAGWorkflow {
    nodes: Vec<Box<dyn WorkflowNode>>,
    router: Box<dyn Fn(&RAGState) -> &'static str>,
}
```

## Alternative Approaches

### Option A: Custom State Machine (Recommended)
Build lightweight state machine tailored to RAG workflows.
- **Pros:** Full control, minimal dependencies, optimal performance
- **Cons:** More code to write and maintain

### Option B: Generic State Machine Library
Use `rust-fsm` or `state-machine` crate.
- **Pros:** Less custom code
- **Cons:** May not fit RAG semantics well, less flexibility

### Option C: Actor Model
Use `actix` actors for workflow nodes.
- **Pros:** Natural async, supervision
- **Cons:** Different paradigm, learning curve
