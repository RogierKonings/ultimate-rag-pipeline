# US-10.3.4: SLO Definitions & Alerts

> **Initiative:** 3 - Unified Cross-Service Observability
> **Priority:** P1
> **Effort:** Medium (2-3 days)
> **Status:** Draft

## Summary

Define Service Level Objectives (SLOs) for the RAG pipeline with automated alerting based on error budgets and burn rates.

## Problem Statement

**Current state**: No formal SLOs defined:
- No documented latency targets
- No error rate thresholds
- No automated alerting on SLO violations
- Reactive rather than proactive incident response

**Impact**:
- No reliability guarantees
- Unclear when to respond to issues
- No basis for capacity planning
- Cannot communicate reliability to stakeholders

## User Story

**As a** SRE
**I want** defined SLOs with automated alerting
**So that** I can ensure reliability targets are met

## Acceptance Criteria

### AC-1: SLO Definitions
- [ ] Retrieval p95 latency < 250ms
- [ ] RAG E2E p95 latency < 2000ms
- [ ] Error rate < 1% per tenant
- [ ] Availability > 99.9%

### AC-2: Error Budget Tracking
- [ ] Monthly error budget calculated
- [ ] Budget consumption visible in dashboard
- [ ] Budget burn rate tracked

### AC-3: Grafana Integration
- [ ] SLO dashboard with burn rate
- [ ] Error budget remaining visualization
- [ ] Historical SLO compliance

### AC-4: AlertManager Rules
- [ ] Multi-window burn rate alerts
- [ ] Severity-based escalation
- [ ] Page only on significant burns

### AC-5: Runbooks
- [ ] Runbook for each alert type
- [ ] Escalation procedures documented
- [ ] Recovery playbooks

## Technical Design

### SLO Definitions

```yaml
# config/slo/definitions.yaml

slos:
  # Retrieval Service SLOs
  retrieval_latency:
    name: "Retrieval Latency"
    description: "Retrieval requests should complete quickly"
    sli:
      type: latency
      metric: "retrieval_search_duration_seconds"
      good_events: "le='0.25'"  # 250ms
    objectives:
      - target: 0.95  # 95% of requests < 250ms
        window: 30d
    alerts:
      - severity: warning
        burn_rate: 2
        window: 1h
      - severity: critical
        burn_rate: 10
        window: 5m

  # RAG E2E SLOs
  rag_e2e_latency:
    name: "RAG End-to-End Latency"
    description: "Complete RAG queries should respond within target"
    sli:
      type: latency
      metric: "rag_e2e_latency_seconds"
      good_events: "le='2.0'"  # 2000ms
    objectives:
      - target: 0.95  # 95% of requests < 2s
        window: 30d
    alerts:
      - severity: warning
        burn_rate: 2
        window: 1h
      - severity: critical
        burn_rate: 10
        window: 5m

  # Error Rate SLOs
  rag_error_rate:
    name: "RAG Error Rate"
    description: "RAG queries should succeed"
    sli:
      type: availability
      good_metric: "rag_queries_total{status='success'}"
      total_metric: "rag_queries_total"
    objectives:
      - target: 0.99  # 99% success rate
        window: 30d
    alerts:
      - severity: warning
        burn_rate: 2
        window: 1h
      - severity: critical
        burn_rate: 14.4  # 100% of 30d budget in 6h
        window: 5m

  # Availability SLOs
  service_availability:
    name: "Service Availability"
    description: "Services should be available"
    sli:
      type: availability
      good_metric: "up{job=~'orchestrator|retrieval|ingestion'}"
      total_metric: "1"
    objectives:
      - target: 0.999  # 99.9% availability
        window: 30d
```

### Prometheus Recording Rules

```yaml
# config/prometheus/slo_rules.yaml

groups:
  - name: slo_recording_rules
    interval: 30s
    rules:
      # Retrieval Latency SLI
      - record: sli:retrieval_latency:ratio_rate5m
        expr: |
          sum(rate(retrieval_search_duration_seconds_bucket{le="0.25"}[5m]))
          /
          sum(rate(retrieval_search_duration_seconds_count[5m]))

      - record: sli:retrieval_latency:ratio_rate1h
        expr: |
          sum(rate(retrieval_search_duration_seconds_bucket{le="0.25"}[1h]))
          /
          sum(rate(retrieval_search_duration_seconds_count[1h]))

      - record: sli:retrieval_latency:ratio_rate30d
        expr: |
          sum(increase(retrieval_search_duration_seconds_bucket{le="0.25"}[30d]))
          /
          sum(increase(retrieval_search_duration_seconds_count[30d]))

      # RAG E2E Latency SLI
      - record: sli:rag_e2e_latency:ratio_rate5m
        expr: |
          sum(rate(rag_e2e_latency_seconds_bucket{le="2.0"}[5m]))
          /
          sum(rate(rag_e2e_latency_seconds_count[5m]))

      - record: sli:rag_e2e_latency:ratio_rate1h
        expr: |
          sum(rate(rag_e2e_latency_seconds_bucket{le="2.0"}[1h]))
          /
          sum(rate(rag_e2e_latency_seconds_count[1h]))

      # Error Rate SLI
      - record: sli:rag_error_rate:ratio_rate5m
        expr: |
          sum(rate(rag_queries_total{status="success"}[5m]))
          /
          sum(rate(rag_queries_total[5m]))

      - record: sli:rag_error_rate:ratio_rate1h
        expr: |
          sum(rate(rag_queries_total{status="success"}[1h]))
          /
          sum(rate(rag_queries_total[1h]))

      # Error Budget Remaining (30d window)
      - record: slo:rag_error_rate:error_budget_remaining
        expr: |
          1 - (
            (1 - sli:rag_error_rate:ratio_rate30d)
            /
            (1 - 0.99)  # 1% error budget
          )

      # Burn Rate (how fast we're consuming error budget)
      - record: slo:rag_error_rate:burn_rate_1h
        expr: |
          (1 - sli:rag_error_rate:ratio_rate1h) / (1 - 0.99)

      - record: slo:rag_error_rate:burn_rate_5m
        expr: |
          (1 - sli:rag_error_rate:ratio_rate5m) / (1 - 0.99)
```

### AlertManager Rules

```yaml
# config/prometheus/slo_alerts.yaml

groups:
  - name: slo_alerts
    rules:
      # Multi-window burn rate alert for error rate
      # Page on high burn rate in short window AND sustained in longer window
      - alert: RAGErrorBudgetBurn_Critical
        expr: |
          slo:rag_error_rate:burn_rate_5m > 14.4
          and
          slo:rag_error_rate:burn_rate_1h > 14.4
        for: 2m
        labels:
          severity: critical
          slo: rag_error_rate
        annotations:
          summary: "RAG error budget burning critically fast"
          description: |
            Burn rate is {{ $value | printf "%.1f" }}x the sustainable rate.
            At this rate, the 30-day error budget will be exhausted in
            {{ printf "%.1f" (div 720 $value) }} hours.
          runbook_url: "https://docs.example.com/runbooks/rag-error-budget"

      - alert: RAGErrorBudgetBurn_Warning
        expr: |
          slo:rag_error_rate:burn_rate_1h > 2
          and
          slo:rag_error_rate:burn_rate_6h > 2
        for: 15m
        labels:
          severity: warning
          slo: rag_error_rate
        annotations:
          summary: "RAG error budget burn rate elevated"
          description: |
            Burn rate is {{ $value | printf "%.1f" }}x sustainable.
            Investigate before budget exhaustion.

      # Latency SLO alerts
      - alert: RetrievalLatencySLO_Critical
        expr: |
          sli:retrieval_latency:ratio_rate5m < 0.90
          and
          sli:retrieval_latency:ratio_rate1h < 0.95
        for: 5m
        labels:
          severity: critical
          slo: retrieval_latency
        annotations:
          summary: "Retrieval latency SLO violation"
          description: |
            Only {{ $value | printf "%.1f" }}% of requests are under 250ms.
            Target is 95%.
          runbook_url: "https://docs.example.com/runbooks/retrieval-latency"

      - alert: RAGE2ELatencySLO_Critical
        expr: |
          sli:rag_e2e_latency:ratio_rate5m < 0.90
          and
          sli:rag_e2e_latency:ratio_rate1h < 0.95
        for: 5m
        labels:
          severity: critical
          slo: rag_e2e_latency
        annotations:
          summary: "RAG E2E latency SLO violation"
          description: |
            Only {{ $value | printf "%.1f" }}% of requests complete under 2s.
            Target is 95%.

      # Error budget exhaustion warning
      - alert: RAGErrorBudgetLow
        expr: |
          slo:rag_error_rate:error_budget_remaining < 0.25
        for: 5m
        labels:
          severity: warning
          slo: rag_error_rate
        annotations:
          summary: "RAG error budget running low"
          description: |
            Only {{ $value | printf "%.1f" }}% of monthly error budget remains.
            Consider freezing non-critical changes.
```

### Runbook Template

```markdown
# Runbook: RAG Error Budget Burn

## Alert: RAGErrorBudgetBurn_Critical

### Description
The error rate is consuming the monthly error budget at an unsustainable rate.
Immediate investigation required.

### Impact
- Users experiencing elevated error rates
- At current rate, budget exhausted in X hours
- May require incident declaration

### Investigation Steps

1. **Check service health**
   ```
   kubectl get pods -n rag-pipeline
   curl -s http://orchestrator:8003/health | jq
   curl -s http://retrieval:8002/health | jq
   ```

2. **Identify error source**
   - Check Grafana dashboard: [RAG Errors](link)
   - Look for specific error types:
     ```
     sum by (error_type) (rate(rag_queries_total{status="error"}[5m]))
     ```

3. **Check dependencies**
   - Qdrant: `curl http://qdrant:6333/health`
   - OpenSearch: `curl http://opensearch:9200/_cluster/health`
   - LLM Gateway: `curl http://llm-gateway:8004/health`

4. **Check recent deployments**
   ```
   kubectl rollout history deployment/orchestrator -n rag-pipeline
   ```

### Mitigation

1. **If Qdrant/OpenSearch unhealthy**:
   - Circuit breaker should activate degraded mode
   - Verify degradation is working: check `retrieval_degradation_mode` metric

2. **If LLM Gateway issues**:
   - Check rate limits
   - Verify model availability

3. **If recent deployment**:
   - Consider rollback:
     ```
     kubectl rollout undo deployment/orchestrator -n rag-pipeline
     ```

4. **If unknown cause**:
   - Enable debug logging temporarily
   - Collect traces for failed requests

### Escalation
- Warning persists > 30 min: Page on-call SRE
- Critical persists > 10 min: Declare incident

### Recovery Verification
- Error rate returns to < 1%
- Burn rate drops below 1x
- No new alerts for 15 min
```
